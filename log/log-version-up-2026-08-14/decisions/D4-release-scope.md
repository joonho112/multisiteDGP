## 3. 버전 번호

### 후보

| 번호 | 논거 |
|---|---|
| **0.2.0** | semver minor. 0.x 대에서는 minor bump 가 breaking change 를 담을 수 있다 |
| 0.9.0 | "1.0 직전" 신호. 그러나 1.0 승격 조건(lifecycle stable, 실사용 cycle)이 충족되지 않았다 |
| 1.0.0 | **불가** — blueprint open question Q8 이 규정한 승격 조건 미충족 |

### breaking change 여부

D1 결정에 따라 갈린다.

| D1 | 사용자 영향 | breaking? |
|---|---|---|
| O4 (solver 양자화) | **수치 동작 변경** + 모든 해시 변경 | **예 — 가장 큼** |
| O2 (허용 오차 해시) | 해시 문자열 변경 (데이터는 불변) | **예** |
| O3 (이중 계약) | 신규 export 추가만 | 아니오 |
| O1 (Linux 재생성) | fixture 해시 변경 | 예 |

D2(광고 축소)도 사용자에게 보이는 변경이다.

### 권고

**`0.2.0`.** 0.x 대이므로 minor bump 로 충분하며, 별도의 신호용 번호를 쓸 이유가 없다.

**단 `NEWS.md` v0.2.0 항목 최상단에 breaking change 절을 둔다:**

- 재현성 계약 변경 (D1 결정 내용 + 이전 해시가 무효임)
- 분포 shape 개수 서술 정정 (D2)
- 기본 테스트 스위트가 이전보다 오래 걸린다 (D3) — 개발자 대상

`tools/cross-os-reproducibility-policy.md` 는 `canonical_hash` 스키마 변경을 "documented major-version reproducibility decision" 사안으로 규정한다. 0.x 대에서 major 는 minor bump 로 대응하는 것이 관례이며, **문서화 요건은 NEWS breaking change 절과 정책 문서 개정으로 충족한다.**
