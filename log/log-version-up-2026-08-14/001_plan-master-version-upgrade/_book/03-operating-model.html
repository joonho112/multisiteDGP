4  실행 규약

4.1 Step 의 정의

Step 은 하나의 AI agent 세션에서 완결되는 최소 작업 단위다. 다음 다섯 가지를 전부 만족해야 Step 이다.

  1. ≤ ~20 분 — agent 실행 시간 기준. 넘으면 쪼갠다.
  2. 단일 관심사 — 하나의 파일 집합, 하나의 결함 군, 하나의 산출물 종류.
  3. 검증 가능한 산출물 — 파일이 생기거나 바뀌거나, 실행 결과가 기록된다. “검토했다” 는 산출물이 아니다.
  4. 명시적 의존 — 어떤 Step 이 먼저 끝나야 하는지 적혀 있다.
  5. 명시적 완료 조건 — “무엇이 참이면 끝인가” 가 적혀 있다.
WarningStep 이 부풀 때

실행 중 Step 이 20 분을 넘길 것 같으면 끝까지 밀지 말고 멈춘다. 세션이 과부하되면 컨텍스트가 요약되면서 정확도가 떨어지고, multi-agent 로 나갈 때 성능이 나오지 않는다. 대신 ① 여기까지의 산출물을 저장하고, ② Phase 로그에 “Step N.M 이 N.Ma / N.Mb 로 분할됨” 을 기록하고, ③ 다음 세션에서 이어간다. Step 분할은 계획 실패가 아니라 정상 운영이다.

4.2 실행 모드

각 Step 은 세 모드 중 하나로 표시된다.

모드 언제 방식
단일 대부분의 실행 작업 — 코드 수정, fixture 재생성, 문서 갱신 agent 1 개가 순차 실행
병렬 감사 넓은 표면을 훑어야 하고 결과가 서로 독립일 때 (Phase 2 대부분) 독립 영역에 agent 를 나눠 던지고 각자 결과를 원장 행으로 반환
다중 관점 설계 판단이 갈릴 수 있고 한 관점의 사각이 치명적일 때 (Phase 3 옵션 비교, Phase 4 hash schema 설계) 서로 다른 프레이밍의 초안 2–3 개 → 합성

병렬 감사와 다중 관점은 PI 가 명시적으로 허용했을 때만 쓴다. 기본은 단일 모드다. 병렬 실행은 토큰 비용이 크고, 결과 합성이 또 하나의 Step 이 된다는 점을 계산에 넣는다.

4.3 Step 실행 프로토콜

모든 Step 이 동일한 6 단계를 따른다.

1. 읽기      해당 Phase 장의 Step 절 + Ch.4 로그 규약 + 부록 A 원장의 관련 행
2. 확인      선행 Step 의 산출물이 실제로 존재하는지 확인 (없으면 중단하고 보고)
3. 실행      작업 수행
4. 검증      완료 조건을 실제로 실행해서 확인 (테스트 실행, 파일 존재, diff 확인)
5. 기록      원장 갱신 + 작업 노트를 Phase 로그 초안에 누적
6. 커밋      단일 논리 커밋. 메시지에 Step 번호 포함 (예: "test(step5.1): replace skip gates")

4 단계를 건너뛰지 않는다. “고쳤으니 됐겠지” 로 다음 Step 에 가면 Phase 종료 시점에 누적된 오류가 한꺼번에 터진다.

4.4 버전 관리 규약

Phase 1 Step 1.2 에서 확정하되, 기본 방침은 다음과 같다.

  • 작업 브랜치. main 에 직접 커밋하지 않는다. Phase 단위 브랜치 upgrade/phase-NN-<slug> 를 쓴다.

  • 커밋 단위. Step 하나 = 커밋 하나가 원칙. Step 안에서 논리적으로 분리되면 여러 개도 허용.

  • 커밋 메시지. Conventional Commits + Step 번호.

    fix(step7.3): drop DPM from advertised shape catalog

DESCRIPTION and NEWS listed DPM as the eighth shape while
gen_effects_dpm() aborts with E22. Ledger row D-014.

  • Phase 병합. Phase 종료 로그 작성 후 main 으로 병합. 원격 push 로 CI 를 태운다.

  • 되돌리기. Phase 4 의 fixture 재생성처럼 되돌리기 비싼 작업은 이전 아티팩트를 log/log-version-up-2026-08-14/artifacts/pre-phase04/ 에 보존한다.

4.5 결함 원장 규약

부록 A 가 스키마를 정의한다. 실제 원장은 다음 경로의 CSV 다.

log/log-version-up-2026-08-14/defect-ledger.csv

원칙:

  • Phase 2 가 원장을 채우고 Step 2.9 에서 닫는다. 이후 Phase 는 원장을 소비한다.
  • 이후 Phase 에서 새 결함이 발견되면 원장에 추가하되 status = deferred-v0.3 이 기본이다. P0 로 올리려면 릴리스를 막을 만한 근거가 있어야 한다.
  • 모든 수정 커밋 메시지는 원장 ID 를 인용한다.
  • Phase 7 종료 시 P0 전건이 fixed 또는 wont-fix (근거 포함) 여야 한다.

4.6 세션 관리

  • 한 세션 = 한 Step 이 기본. 짧은 Step 2–3 개를 묶는 것은 허용하되, 파일 집합이 겹치지 않을 때만.
  • 컨텍스트 오염 방지. 감사 Step (Phase 2) 은 읽기 위주라 컨텍스트를 크게 먹는다. 감사 Step 과 수정 Step 을 같은 세션에 섞지 않는다.
  • 핸드오프. 세션을 넘길 때는 ① 완료한 Step, ② 진행 중이던 Step 의 중단 지점, ③ 다음 Step 번호를 Phase 로그 초안에 적는다.
  • 긴 실행. R CMD check, 전체 테스트, validation experiment 는 백그라운드로 돌리고 그 사이 다른 일을 한다. 결과를 기다리며 세션을 놀리지 않는다.

4.7 Phase 종료 프로토콜

Phase 의 마지막 Step 이 끝나면 항상 다음을 수행한다.

  1. Phase 게이트 검증 — 해당 Phase 장의 “Phase 종료 조건” 을 실제로 실행해 확인
  2. Phase 로그 작성 — Ch.4 로그 규약 에 따라 qmd 작성 후 html 렌더
  3. 원장 갱신 — 이 Phase 에서 처리된 행의 status 갱신
  4. 브랜치 병합 + push — CI 실행
  5. 다음 Phase 진입 판단 — 게이트 Phase (3, 10) 는 승인 대기

4.8 PI 게이트

두 곳에서 실행이 멈추고 PI 승인을 기다린다.

게이트 위치 승인 대상
G-A 이 계획서 Phase / Step 구조, 범위, 버전 목표
G-B Phase 3 Step 3.5 재현성 계약 재설계안, 광고-구현 갭 처리 방침, 테스트 게이트 정책, 최종 버전 번호

G-B 없이 Phase 4 로 진입하지 않는다. hash schema 변경과 광고 축소는 되돌리기 비싸고 사용자 영향이 있는 결정이므로 agent 가 단독으로 정하지 않는다.

Phase 10 은 외부 리뷰 게이트다. 리뷰어(GPT Codex 또는 별도 Claude 세션) 는 리뷰 패킷만 받고 계획 내부는 보지 않는다 — 계획의 프레이밍이 리뷰를 오염시키지 않게 하기 위해서다.

4.9 작업 디렉터리 지도

multisiteDGP-R-package/
├─ R/  tests/  man/  vignettes/  inst/  tools/   ← package 본체 (수정 대상)
├─ .github/workflows/                            ← CI (Phase 6 대상)
├─ blueprint-multisiteDGP-book/                  ← 설계 근거 (읽기 전용)
├─ multisiteDGP-build-implementation-book/       ← 구현 이력 (읽기 전용)
├─ documentation-updates/                        ← 문서 오버홀 이력 (읽기 전용)
└─ log/log-version-up-2026-08-14/                ← 이번 작업 공간
   ├─ 001_plan-master-version-upgrade/           ← 이 책
   ├─ 002_phase01-*.qmd/.html … 012_phase11-*    ← Phase 종료 로그
   ├─ defect-ledger.csv                          ← 결함 원장 (Phase 2 산출)
   ├─ decisions/                                 ← Phase 3 결정 문서
   ├─ evidence/                                  ← 감사 원자료 (CI 로그, 테스트 출력 등)
   └─ artifacts/                                 ← 되돌리기용 보존 아티팩트

읽기 전용으로 표시된 세 book 은 수정하지 않는다. 이들은 과거 작업의 감사 추적이며, 현재와 어긋나는 부분이 있어도 그것은 결함이 아니라 이력이다. 현재 상태를 반영해야 하는 것은 tools/traceability/ 의 ledger CSV 이며 Phase 9 Step 9.5 가 담당한다.
