0.1 이 책은 무엇인가

이 책은 multisiteDGP R package 를 v0.1.1 → v0.2.0 으로 끌어올리는 master plan 이다. 작업 전체를 11 개의 선형 Phase 와 각 Phase 안의 Step (하나당 AI agent 가 한 세션에 소화할 수 있는 ≤ ~20 분 분량) 으로 분해하고, 각 Step 의 목표 · 산출물 · 소요 시간 · 의존 관계를 명시한다. 실행 규약, 로그 규약, 인수 기준도 함께 잠근다.

작성일은 2026-08-14, 작성 주체는 Claude Opus 5 planning agent 이며, 근거는 다음 다섯 가지다.

  • package source 전수 (R/ 35 파일 10,287 줄, tests/ 71 파일 7,836 줄, vignettes/ 16 편, DESCRIPTION, NAMESPACE, NEWS.md)
  • 실측 진단 — 로컬 테스트 스위트 2 회 실행 (기본 / slow+property 게이트 on), R CMD check --as-cran 1 회 실행
  • 원격 CI 포렌식 — joonho112/multisiteDGP GitHub Actions 실행 이력 15 건, extended-tests 실패 로그 전문
  • 기존 설계 문서 — blueprint-multisiteDGP-book/ 25 장, multisiteDGP-build-implementation-book/ (127 로그), documentation-updates/ (99 로그)
  • 미해결 항목 원장 — documentation-updates/working/06-final-punch-list.md, blueprint ch.24 roadmap, ch.25 open questions

0.2 왜 지금 이 작업인가

PI 의 문제 인식은 “IES annual report 마감에 쫓겨 급하게 만든 package 라 문제가 많다” 였다. 진단 결과 그 인식은 절반만 맞다.

나쁜 소식이 아니었던 부분. package 의 코드 와 문서 표면 은 생각보다 견고하다. 2026-05 의 10-Phase 문서 오버홀이 roxygen 53 exports · vignette 16 편 · pkgdown 사이트를 이미 public-release 수준으로 올려놓았고, slow / property 게이트를 켜고 돌린 전체 테스트 스위트는 로컬에서 T1a 하나만 skip 되고 전부 통과한다. R CMD check --as-cran 도 로컬에서 0 error / 0 warning 이다.

진짜 나쁜 소식. 문제는 코드가 아니라 package 를 둘러싼 공학 기반(engineering substrate) 이 무너져 있다는 것이다.

  1. 로컬 작업본이 git repository 가 아니다. .git 이 없다. 원격 joonho112/multisiteDGP 는 PUBLIC 으로 살아 있고 마지막 push 는 2026-05-10 이다. 즉 지금 PI 의 디스크에 있는 것과 세상에 공개된 것 사이에 3 개월의 미확인 격차 가 있고, 어느 쪽이 최신인지 확인할 수단이 없다.
  2. CI 가 3 개월째 전부 red 다. 마지막 push 시점의 R-CMD-check, lint, test-coverage 가 모두 실패했고, 주간 스케줄로 도는 extended-tests 는 2026-05-11 부터 2026-07-13 까지 10 주 연속 실패했다. 성공한 workflow 는 pkgdown-deploy 하나뿐이다. 그래서 공개 사이트만 멀쩡해 보인다.
  3. 로컬 green 이 green 이 아니다. 기본 devtools::test() 는 30 개 테스트를 skip 한다. 표준화 계약(T13–T17), property invariant(P01–P12), 분포 검정(T1b, T4, T9) 이 전부 환경 변수 뒤에 숨어 있다. 개발자가 평소에 보는 “💅 Your tests are beautiful 💅” 는 통계적 정확성을 거의 검증하지 않은 상태의 green 이다.
  4. 재현성 계약이 문서와 아티팩트 사이에서 모순된다. tools/cross-os-reproducibility-policy.md 는 Linux x86_64 를 authoritative baseline 으로 규정하는데, 실제 체크인된 golden fixture 9 개와 print-example snapshot 은 macOS/aarch64 에서 생성됐다. 이 모순이 extended-tests 10 주 연속 실패의 직접 원인이다.
  5. 광고와 구현이 어긋난다. DESCRIPTION 은 “eight distribution shapes … and a Dirichlet-process-mixture bridge” 를 광고하지만 true_dist = "DPM" 은 호출 즉시 hard abort 하는 stub 이다. target_marginal_rho 인자도 존재하지만 E23 으로 abort 한다.

이 다섯 가지는 전부 “코드를 더 쓰면 해결되는” 문제가 아니라 계약 · 기반 · 정직성 의 문제다. v0.2.0 을 신뢰성 릴리스(reliability release) 로 규정하는 이유가 여기 있다.

0.3 이 책이 아닌 것

  • 산출물 자체가 아니다. 이 책은 v0.2.0 을 만드는 playbook 이지, v0.2.0 의 코드 · 문서 · fixture 가 아니다.
  • 기능 추가 로드맵이 아니다. blueprint ch.24 의 v1.x / v2.0 feature roadmap (as_lme4(), as_brms(), Student-t copula, vector-valued effects 등) 은 이 계획의 범위 밖이다. v0.2.0 은 기존 표면을 믿을 수 있게 만드는 릴리스다. 예외는 이미 광고된 표면의 갭(DPM, marginal target)뿐이며, 그것도 “구현” 과 “정직하게 축소” 중 어느 쪽을 택할지는 Phase 3 에서 PI 가 결정한다.
  • 문서 오버홀이 아니다. 2026-05 오버홀로 만들어진 문서 표면은 그대로 둔다. Phase 9 는 v0.2.0 에서 실제로 바뀐 동작만 문서에 반영하는 델타 동기화다.

0.5 Phase / Step 구조 요약

11 Phase, 67 Step. Phase 3 와 Phase 10 은 PI / 외부 리뷰 게이트이며, 통과 없이 다음 Phase 로 진행하지 않는다.

합계 67 ~21 시간

누적 시간은 agent 실행 시간만 계산한 것이며, PI 검토 대기 · CI 실행 대기 · 외부 리뷰 왕복은 포함하지 않는다. 실제 달력 시간은 CI 매트릭스 왕복(Phase 4 · 6 · 11)과 외부 리뷰 왕복(Phase 10)이 지배한다.

0.7 이 계획을 승인한 뒤

PI 가 이 책을 검토하고 승인하면 Step 1.1 부터 실행한다. Phase 3 (Step 3.5) 에서 한 번 더 PI 승인이 필요하다 — 재현성 계약 재설계안과 광고-구현 갭 처리 방침은 되돌리기 비싼 결정이므로 agent 가 단독으로 정하지 않는다.
