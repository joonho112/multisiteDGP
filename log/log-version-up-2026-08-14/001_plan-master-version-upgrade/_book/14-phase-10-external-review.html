15  Phase 10 — 외부 리뷰 게이트

15.1 목표

계획을 만든 주체가 아닌 눈으로 v0.2.0 을 검토받고, 발견을 처리한다.

2026-05 오버홀은 GPT Codex 3 라운드 리뷰를 거쳤고, 그것이 품질에 실질적으로 기여했다 (NEWS.md 가 명시). 같은 구조를 이번에도 쓴다. 다만 이번 릴리스는 문서가 아니라 동작과 계약 이 대상이므로 리뷰 초점이 다르다.

Step 수 5 (10.1 – 10.5)
누적 시간 ~95 분 (+ 리뷰 왕복 대기)
선행 Phase Phase 9
종료 로그 011_phase10-external-review.qmd
게이트 외부 리뷰 — Critical 발견 미해소 시 Phase 11 진입 금지
Note리뷰어 격리

리뷰어에게는 리뷰 패킷과 package 만 준다. 이 계획서, Phase 로그, 결함 원장은 주지 않는다. 계획의 프레이밍이 리뷰를 오염시키면 “우리가 이미 아는 것” 만 확인받게 된다. 리뷰어가 우리가 놓친 것을 찾게 하려면 백지에서 봐야 한다.

15.2 Step 10.1 — 리뷰 패킷 작성

항목 값
모드 단일
소요 ~20 분
의존 Phase 9

목표. 리뷰어가 맥락 없이도 판단할 수 있는 패킷을 만든다.

패킷 구성.

  1. 대상 서술 — package 가 무엇을 하는 것인지 (README 수준). v0.2.0 이 무엇을 바꿨는지 (NEWS 수준)
  2. 리뷰 초점 4 개 — 이번 릴리스의 성격에 맞춰
    • 초점 1 — 재현성 계약. 계약이 명확한가? 문서 · 코드 · 테스트 · fixture 가 일관되는가? 사용자가 이 계약으로부터 무엇을 기대할 수 있는지 알 수 있는가?
    • 초점 2 — 정직성. package 가 약속하는 것과 하는 것이 일치하는가? 미구현 기능이 명확히 표시되는가? 오류 메시지가 사용자를 올바른 방향으로 보내는가?
    • 초점 3 — 테스트가 실제로 검증하는가. 테스트가 통과한다는 것이 무엇을 의미하는가? 축소된 테스트가 여전히 실제 위반을 잡는가? 놓친 불변량이 있는가?
    • 초점 4 — 통계적 타당성. DGP 의 수학적 주장이 구현과 일치하는가? 표준화 규약, dependence injection, 진단 수식
  3. 진입점 — 리뷰어가 어디부터 볼지: README.md, NEWS.md, vignette("m1"), vignette("m7"), R/utils-reproducibility.R, tests/testthat/
  4. 명시적 질문 목록 — 리뷰어에게 답을 요청할 것 (아래 §참조)
  5. 비-질문 — 리뷰 범위 밖: 문서 문체, v0.3 기능 제안, 아키텍처 재설계

리뷰어에게 던질 질문 (초안).

  • 재현성 계약을 읽고, 다른 컴퓨터에서 동일 결과를 얻으려면 무엇을 해야 하는지 말할 수 있는가?
  • DESCRIPTION / NEWS / vignette 를 읽고 실제로 동작하지 않는 기능을 광고하는 곳을 찾을 수 있는가?
  • 테스트 스위트를 보고, 통과하는데도 놓칠 수 있는 결함을 상상할 수 있는가?
  • 어느 수학적 주장이 구현에서 증명되지 않는가?

산출물.

  • log/log-version-up-2026-08-14/review-packet/ — 패킷 문서 + 진입점 목록
  • 패킷 렌더본

완료 조건.

  • 패킷이 계획서 · 로그 · 원장을 참조하지 않고 자기 완결적이다
  • 4 개 초점과 질문 목록이 있다
  • 범위 밖 항목이 명시되어 있다

15.3 Step 10.2 — 리뷰 수신 및 트리아지

항목 값
모드 단일
소요 ~20 분
의존 10.1 + 리뷰어 응답

목표. 리뷰 발견을 분류하고 처리 계획을 세운다.

작업.

  1. 리뷰 결과를 review-packet/round-1/findings.md 로 보존 (원문 그대로)
  2. 각 발견을 분류
    • Critical — 릴리스를 막는다. 잘못된 동작, 위험한 문서, 계약 모순
    • Important — 고쳐야 하지만 릴리스를 막지는 않는다
    • Minor — 개선 제안
    • Rejected — 동의하지 않는다. 반드시 근거를 남긴다. 리뷰어가 틀릴 수 있고, 그 판단도 기록되어야 한다
  3. 각 발견을 재현으로 검증 — 리뷰어의 지적이 실제로 성립하는지 확인. 성립하지 않으면 Rejected + 근거
  4. Critical / Important 를 원장에 등재 (source = external-review-r1)
  5. 처리 계획 — Step 10.3 / 10.4 배정

산출물.

  • review-packet/round-1/findings.md — 원문
  • review-packet/round-1/triage.md — 분류 + 검증 결과 + 배정
  • 원장 신규 행

완료 조건.

  • 모든 발견이 4 분류 중 하나로 배정되어 있다
  • 각 발견이 재현으로 검증되어 있다
  • Rejected 각각에 근거가 있다

15.4 Step 10.3 — 리메디에이션 ①: Critical

항목 값
모드 단일
소요 ~20 분
의존 10.2

목표. Critical 발견을 전부 해소한다.

작업.

  1. Critical 각각에 대해 Phase 7 과 동일 절차 — 회귀 테스트 먼저, 수정, 검증
  2. 수정이 Phase 4/5/7/8/9 산출물에 영향을 주면 해당 Phase 의 검증을 부분 재실행
    • 수치 동작 변경 → Phase 8 의 관련 validation 재실행
    • fixture 변경 → Phase 4 의 재생성 절차
    • 문서 변경 → Phase 9 의 정합성 스캔
  3. 각 수정을 별도 커밋. 메시지에 발견 ID
  4. 수정 후 전체 테스트 + R CMD check

산출물.

  • 수정 + 커밋
  • 원장 status 갱신
  • 영향받은 이전 Phase 산출물의 재검증 기록

완료 조건.

  • Critical 전건이 fixed 이다
  • 각 수정에 회귀 테스트가 있다
  • 전체 테스트와 check 가 통과한다

15.5 Step 10.4 — 리메디에이션 ②: Important

항목 값
모드 단일
소요 ~20 분
의존 10.3

목표. Important 발견을 처리하거나 v0.3 으로 이월한다.

작업.

  1. Important 각각에 대해: 처리 비용 추정 → v0.2.0 에서 처리 vs v0.3 이월 판단
  2. 처리하는 것은 Step 10.3 과 동일 절차
  3. 이월하는 것은 GitHub Issue 로 등록하고 원장 status 를 deferred-v0.3
  4. Minor 는 전부 v0.3 백로그 (Issue) — 단 5 분 안에 끝나는 것은 처리해도 된다

산출물.

  • 수정 + 커밋
  • GitHub Issues (이월분)
  • 원장 status 갱신

완료 조건.

  • Important 전건이 fixed 또는 deferred-v0.3 (Issue 링크) 이다
  • Minor 가 전부 Issue 로 등록되어 있다

15.6 Step 10.5 — 리뷰 종료 및 2 차 라운드 판단

항목 값
모드 단일
소요 ~15 분
의존 10.3, 10.4

목표. 리뷰 라운드를 닫고, 2 차 라운드가 필요한지 판단한다.

작업.

  1. 리메디에이션 요약 — 발견 × 처리 × 커밋
  2. 2 차 라운드 판단 기준
    • Critical 이 3 건 이상이었다 → 2 차 권장 (1 차가 놓친 것이 더 있을 가능성)
    • Critical 수정이 아키텍처를 건드렸다 → 2 차 필수
    • Critical 0–2 건이고 수정이 국소적이었다 → 2 차 불필요
  3. 2 차가 필요하면 Step 10.1–10.5 를 반복 (round-2/). 로그 번호는 다음 번호를 가져간다
  4. 리뷰 아카이브 정리 — review-packet/ 이 자기 완결적인지 확인
  5. 리뷰가 놓친 것 자기 평가 — 우리가 아는 문제 중 리뷰어가 지적하지 않은 것이 있는가? 있다면 패킷이 그 영역을 가렸을 수 있다. 다음 리뷰를 위해 기록

산출물.

  • review-packet/round-1/closeout.md
  • 2 차 라운드 판단 + 근거

완료 조건.

  • 리뷰 라운드가 종료 문서로 닫혀 있다
  • 2 차 필요 여부가 기준에 따라 판단되어 있다
  • 리뷰 아카이브가 자기 완결적이다
