8  Phase 3 — v0.2.0 범위 결정

8.1 목표

되돌리기 비싼 결정을 PI 승인 아래 확정한다. Phase 2 가 결함을 알아냈다면 Phase 3 은 무엇을 어떻게 고칠지 를 정한다. 네 가지 결정이 Phase 4–7 의 작업 내용을 좌우한다.

결정 왜 PI 승인이 필요한가
D1 — 재현성 계약 재설계 hash schema 변경은 기존 fixture · 논문 재현 증거 · 사용자 코드에 영향. cross-os-reproducibility-policy.md 는 이를 “major-version reproducibility decision” 사안으로 규정
D2 — 광고-구현 갭 처리 DPM 을 광고에서 빼는 것은 사용자에게 보이는 축소. IES 보고서에서 이미 8 shape 를 언급했을 수 있음
D3 — 테스트 게이트 정책 게이트를 없애면 CI 시간과 개발 루프 시간이 늘어난다. 비용/편익 판단
D4 — 버전 번호와 릴리스 범위 P0 개수에 따라 v0.2.0 에 넣을 것과 v0.3 으로 미룰 것이 갈린다

Phase 3 은 아무것도 구현하지 않는다. 옵션을 비교하고, 근거를 정리하고, PI 결정을 받는다.

Step 수 5 (3.1 – 3.5)
누적 시간 ~90 분 (+ PI 검토 시간)
선행 Phase Phase 2 (원장 확정)
종료 로그 004_phase03-scope-decisions.qmd
게이트 G-B — PI 승인 없이 Phase 4 진입 금지

8.2 Step 3.1 — D1: 재현성 계약 재설계 옵션 비교

항목 값
모드 다중 관점 (3 옵션 각각을 옹호하는 관점으로 작성 후 비교)
소요 ~25 분
의존 Step 2.3 (드리프트 발생 지점 특정)

목표. Step 2.3 이 특정한 드리프트 원인을 놓고, 재현성 계약을 어떻게 다시 설계할지 옵션을 비교한다.

옵션 (Step 2.3 결과에 따라 조정 가능).

옵션 내용 장점 단점
O1 — 현행 유지 + 아티팩트 정정 hash schema 그대로. golden fixture / snapshot 을 Linux 에서 재생성해 정책과 일치시킨다 최소 변경, 계약 불변, 기존 재현 증거 유지 macOS/Windows 개발자는 여전히 로컬에서 T1a 검증 불가. 드리프트 원인 자체는 남음
O2 — 허용 오차 기반 해시 해시 전에 수치를 정해진 유효자리로 정규화(round). 플랫폼 간 동일 해시 달성 세 플랫폼 전부에서 계약 검증 가능. 개발 루프 개선 schema 변경 → 기존 hash 전부 무효. 정규화 자리수 선택이 자의적. 진짜 수치 회귀를 가릴 위험
O3 — 이중 계약 비트 해시(canonical_hash)는 same-machine 용으로 유지 + 별도 stable_hash (허용 오차 기반)를 cross-platform 계약으로 추가 두 목적을 분리. 기존 계약 보존 + 새 계약 추가 표면 증가, 두 해시의 용도 혼동 위험, 문서 부담

작업.

  1. Step 2.3 의 드리프트 크기 수치를 근거로 각 옵션의 실현 가능성 평가. 드리프트가 1–2 ULP 면 O2 가 안전하고, 크면 O2 는 진짜 문제를 가린다
  2. 각 옵션에 대해: 구현 범위(어느 파일, 몇 Step), 영향 받는 아티팩트(fixture / snapshot / vignette / traceability ledger), 사용자 영향, 되돌리기 비용
  3. JEBS 논문 재현성 영향 평가 — golden fixture 는 Lee et al. (2025) 부록 재현 증거다. 각 옵션이 이 증거를 어떻게 처리하는지가 결정적
  4. cross-os-reproducibility-policy.md 를 각 옵션에 맞게 개정할 때 바뀌는 조항 열거
  5. 권고안 1 개 제시 + 근거

산출물.

  • log/log-version-up-2026-08-14/decisions/D1-reproducibility-contract.md — 옵션 3 개 비교표 + 권고안 + PI 결정란
  • 각 옵션의 Phase 4 Step 구성 초안

완료 조건.

  • 3 옵션 각각에 구현 범위 · 영향 · 되돌리기 비용이 명시되어 있다
  • JEBS 재현 증거에 대한 영향이 각 옵션별로 평가되어 있다
  • 권고안과 근거가 있다

8.3 Step 3.2 — D2: 광고-구현 갭 처리 방침

항목 값
모드 단일
소요 ~20 분
의존 Step 2.4

목표. Step 2.4 가 확정한 갭 각각에 대해 구현 / 광고 축소 / 명시적 deprecate 중 하나를 배정한다.

작업.

각 갭에 대해 세 선택지를 비용과 함께 제시한다.

갭 선택지 A (구현) 선택지 B (광고 축소) 선택지 C (명시적 실험 기능)
DPM dirichletprocess 또는 NIMBLE wrap. blueprint §24.2.1 이 v2.0 으로 미룬 항목 — 표준화 recipe 가 sample-dependent 라는 blocker 존재 DESCRIPTION / NEWS 에서 “eight shapes” → “seven shapes + DPM bridge (미구현)”. gen_effects_dpm() 은 stub 유지 lifecycle::experimental 배지 + 명시적 “미구현” 문서. export 유지
target_marginal_rho blueprint §24.2.7 이 v2.0 으로 미룬 항목 — PSD compatibility bound 구현 필요 인자 제거 또는 문서에서 숨김. E23 메시지를 “v2 예정” 으로 명확화 현행 유지 + 문서 명확화
upstream 용도 불명 — 먼저 무엇을 위한 인자인지 blueprint 에서 확인 인자 제거 현행 유지
SkewN audit resolver R/diagnostics-core.R Group C resolver 확장. punch list 는 60–90 분 추정 M2 vignette 에 한계 명시 (punch list 기본안, ~10 분) —

작업 순서.

  1. 각 갭의 실제 구현 비용 을 blueprint 의 blocker 서술과 대조해 재추정
  2. 사용자 영향 평가 — IES annual report, JEBS 논문, 기존 사용자 코드에서 해당 기능을 언급/사용하는가?
  3. 각 갭에 권고 선택지 배정
  4. 선택지 B(광고 축소)를 택한 갭에 대해 바꿔야 할 문서 위치 전수 열거 — DESCRIPTION, NEWS.md, README.Rmd, index.md, roxygen, vignette, pkgdown

산출물.

  • decisions/D2-advertised-surface.md — 갭 × 선택지 × 비용 × 권고 + PI 결정란
  • 선택지 B 채택 시 수정 대상 문서 위치 목록

완료 조건.

  • Step 2.4 가 찾은 모든 갭에 권고 선택지가 배정되어 있다
  • 각 권고에 구현 비용 추정과 사용자 영향 평가가 있다
  • 광고 축소 대상의 문서 위치가 전수 열거되어 있다

8.4 Step 3.3 — D3: 테스트 게이트 정책 재설계

항목 값
모드 단일
소요 ~15 분
의존 Step 2.2 (skip 매트릭스, slow 테스트 타이밍)

목표. 30 개 skip 을 어떻게 없앨지 정한다. 목표는 성공 기준 G3 — 기본 devtools::test() 의 skip ≤ 3 이다.

작업.

  1. Step 2.2 의 타이밍 자료를 근거로 각 slow 테스트를 4 분류
    • 그대로 켠다 — 실행 비용이 실제로 낮음. 게이트가 관성으로 남아 있던 것
    • 비용을 줄여서 켠다 — 표본 크기 / 반복 수 / 격자 크기를 통계적 검정력을 유지하며 축소
    • 분할한다 — 빠른 핵심 검증은 기본, 전수 격자는 확장 스위트
    • 확장 스위트로 남긴다 — 정당한 사유가 있는 것만. 사유를 문서화
  2. 기본 스위트 시간 예산 설정 — 목표: 기본 devtools::test() 가 N 분 이내. N 을 정한다 (권고: 3 분)
  3. 확장 스위트 재정의 — 무엇이 남는가? extended-tests workflow 가 무엇을 돌리는가?
  4. property 테스트 처리 — hedgehog 를 Suggests 로 유지할지, 게이트를 없앨지
  5. 플랫폼 게이트 처리 — skip_if_not_linux_strict_hash() 는 D1 결정에 종속. O2/O3 를 택하면 이 게이트는 사라진다

산출물.

  • decisions/D3-test-gate-policy.md — 테스트별 4 분류 배정 + 시간 예산 + PI 결정란

완료 조건.

  • 현재 게이트된 30 개 테스트 전부에 4 분류 중 하나가 배정되어 있다
  • 기본 스위트 목표 시간이 정해져 있다
  • 확장 스위트에 남기는 것 각각에 사유가 있다

8.5 Step 3.4 — D4: 버전 번호와 릴리스 범위 확정

항목 값
모드 단일
소요 ~15 분
의존 3.1, 3.2, 3.3, Step 2.9

목표. 원장의 P0/P1 을 v0.2.0 에 넣을 것과 v0.3 으로 미룰 것으로 나누고, 버전 번호를 확정한다.

작업.

  1. P0 용량 검토 — Phase 4/5/7 이 소화할 수 있는 Step 수는 각각 ~7. P0 개수가 이를 넘으면 일부를 P1 로 강등하거나 Phase 를 늘린다
  2. 버전 번호 결정
    • D1 이 O1(현행 유지)이면 → 0.2.0
    • D1 이 O2(schema 변경)면 → 정책상 “major-version reproducibility decision” 에 해당. 0.2.0 으로 가되 NEWS 에 breaking change 를 명시할지, 아니면 다른 번호를 쓸지 판단
    • D2 가 광고 축소를 포함하면 → 사용자에게 보이는 축소이므로 NEWS 상단에 명시
  3. v0.3 백로그 확정 — 미룬 항목을 dev/NEWS-internal.md 또는 GitHub Issues 로. GitHub Issues 사용을 권고 — 현재 이슈 0 건이며, 백로그를 저장소 밖에 두면 또 잊힌다
  4. 릴리스 일정 초안 — Phase 4–11 의 예상 소요와 CI 왕복 시간을 반영

산출물.

  • decisions/D4-release-scope.md — v0.2.0 포함/제외 목록 + 버전 번호 + 백로그 이관 계획 + PI 결정란

완료 조건.

  • 원장의 모든 P0/P1 행이 “v0.2.0 포함” 또는 “v0.3 백로그” 로 배정되어 있다
  • 버전 번호가 근거와 함께 제안되어 있다
  • v0.2.0 포함분이 Phase 4/5/7 의 Step 용량에 들어간다

8.6 Step 3.5 — PI 승인 패킷 작성 및 제출

항목 값
모드 단일
소요 ~15 분
의존 3.1 – 3.4

목표. PI 가 10 분 안에 읽고 결정할 수 있는 승인 패킷을 만든다. 네 결정을 한 문서에 모으고, 각각에 권고안과 결정란을 둔다.

작업.

  1. D1–D4 결정 문서를 한 패킷으로 통합. 각 결정마다:
    • 한 문단 배경 (왜 이 결정이 필요한가)
    • 옵션 표 (선택지 × 비용 × 영향)
    • 권고안 1 개 와 근거 3 줄
    • 결정란 (승인 / 대안 선택 / 보류)
  2. 패킷 맨 앞에 1 페이지 요약 — 네 결정과 네 권고안만
  3. 각 결정이 되돌릴 수 있는지 표시
  4. 결정이 늦어질 때 무엇이 막히는지 표시 (D1 → Phase 4 전체, D2 → Phase 7 일부, D3 → Phase 5 전체, D4 → 없음)

산출물.

  • decisions/000-PI-approval-packet.md — 통합 패킷
  • decisions/000-PI-approval-packet.html — 렌더본 (PI 가 읽기 편하게)

완료 조건.

  • 네 결정 전부에 권고안과 결정란이 있다
  • 1 페이지 요약이 있다
  • 패킷이 렌더되어 있다
Important게이트 G-B

이 Step 이후 실행을 멈추고 PI 결정을 기다린다. PI 결정 없이 Phase 4 로 진입하지 않는다. 결정이 도착하면 각 결정 문서의 결정란을 채우고 Phase 3 로그를 완성한 뒤 Phase 4 를 시작한다.
