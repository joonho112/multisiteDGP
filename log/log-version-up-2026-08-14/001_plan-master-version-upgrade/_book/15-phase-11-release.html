16.1 목표

성공 기준 G1–G7 을 전부 실증하고 v0.2.0 을 릴리스한다. 그리고 v0.3 을 위한 인계 문서를 남긴다.

Step 수 5 (11.1 – 11.5)
누적 시간 ~85 분 (+ CI 실행 대기)

16.2 Step 11.1 — 전체 로컬 게이트

항목 값
모드 단일
소요 ~20 분 (+ 실행 대기)
의존 Phase 10

목표. Step 1.5 와 동일한 명령으로 재측정해서 개선을 수치로 증명한다.

작업. Step 1.5 의 7 개 측정을 그대로 재실행한다.

측정 베이스라인 (Step 1.5) 목표
기본 테스트 30 skip skip ≤ 3
확장 테스트 1 skip (T1a) skip 0 또는 사유 기록
check (기본) 0E/0W/2N 0E/0W, NOTE 문서화
check (전체, vignette 포함) Step 1.5 측정값 0E/0W, NOTE 문서화
커버리지 Step 1.5 측정값 베이스라인 이상
lint Step 1.5 측정값 0 위반 (또는 문서화된 예외)
성능 Step 1.5 측정값 유의한 회귀 없음

작업.

  1. 7 개 측정 실행 (긴 것은 백그라운드 병행)
  2. before/after 비교표 작성
  3. 목표 미달 항목이 있으면 원인 파악 → 수정하거나 사유 기록
  4. 2 회 연속 실행으로 플레이키 확인

산출물.

  • evidence/phase11/final-metrics.md — before/after 비교표
  • evidence/phase11/final-raw/ — 원본 출력 7 개

완료 조건.

  • 7 개 측정이 재실행되고 비교표가 있다
  • 목표 미달 항목이 없거나, 있으면 사유가 기록되어 있다
  • 2 회 실행 결과가 동일하다

16.3 Step 11.2 — CI 최종 매트릭스 확인

항목 값
모드 단일
소요 ~20 분 (+ CI 대기)
의존 11.1

목표. 릴리스 후보 커밋에서 전체 CI 가 green 임을 확인한다.

작업.

  1. 릴리스 후보를 main 에 병합하고 push
  2. 6 개 workflow 전부 실행 확인
    • R-CMD-check 5 cell
    • lint, test-coverage, extended-tests, pkgdown-deploy
  3. 각 cell 의 출력을 보존 — GitHub 로그는 90 일 후 만료된다. 핵심 출력을 evidence/phase11/ci-final/ 에 저장
  4. extended-tests 를 수동 실행(workflow_dispatch)해서 green 확인 — 스케줄을 기다리지 않는다
  5. Windows cell 의 snapshot 테스트 통과 확인 — Phase 4/5 에서 Linux · macOS 만 로컬 검증했으므로, Windows 는 여기가 첫 확인

산출물.

  • evidence/phase11/ci-final/ — workflow 별 출력 보존
  • run ID 목록

완료 조건.

  • 6 개 workflow 전부 green (성공 기준 G2)
  • Windows cell 이 통과한다
  • 출력이 보존되어 있다

16.4 Step 11.3 — 릴리스 아티팩트 생성

항목 값
모드 단일
소요 ~15 분
의존 11.2

목표. 배포 가능한 아티팩트를 만들고 검증한다.

작업.

  1. R CMD build 로 tarball 생성 — multisiteDGP_0.2.0.tar.gz
  2. tarball 검증
    • 크기 (Step 1.4 의 baseline 대비)
    • 포함 파일 목록 — .Rbuildignore 가 제대로 동작하는가? log/, blueprint-*, documentation-updates/, tools/ 가 빠졌는가?
    • tarball 에서 설치 → library(multisiteDGP) → 기본 동작 확인
  3. 깨끗한 환경에서 설치 검증 — 새 R 라이브러리 경로에 설치하고 Suggests 없이 기본 기능이 동작하는지
  4. R CMD check 를 tarball 에 대해 실행 (source directory 가 아니라)
  5. 릴리스 노트 작성 — NEWS.md v0.2.0 항목을 기반으로 GitHub Release 본문

산출물.

  • multisiteDGP_0.2.0.tar.gz
  • evidence/phase11/tarball-verification.md
  • 릴리스 노트 초안

완료 조건.

  • tarball 이 생성되고 검증됐다
  • 깨끗한 환경에서 설치·동작한다
  • tarball 대상 R CMD check 가 통과한다
  • 불필요한 파일이 tarball 에 없다

16.5 Step 11.4 — 태그 및 배포

항목 값
모드 단일
소요 ~15 분
의존 11.3

목표. 버전을 태그하고 공개한다.

ImportantPI 확인 필요

GitHub Release 생성은 외부에 공개되는 행위다. 태그 생성과 Release 발행 전에 PI 확인을 받는다. Step 11.3 까지 완료된 상태를 보고하고 승인을 받은 뒤 진행한다.

작업.

  1. v0.2.0 태그 생성 (annotated) 후 push
  2. GitHub Release 생성 — 릴리스 노트 + tarball 첨부
  3. pkgdown-deploy 가 실행되어 사이트가 갱신되는지 확인
  4. 공개 사이트 확인 — https://joonho112.github.io/multisiteDGP/
    • 버전 표시가 0.2.0
    • NEWS 페이지에 v0.2.0 항목
    • reference index 에 신규 export (있다면)
    • vignette 16 편 접근 가능
  5. _pkgdown.yml 의 development: mode: unreleased 검토 — 태그된 릴리스가 생겼으므로 release 또는 auto 로 바꿀지 판단
  6. 재현성 최종 확인 — 공개된 tarball 을 다운로드해서 설치하고 README 의 hash check 예제를 실행. 문서화된 값이 나오는가?

산출물.

  • v0.2.0 태그 (로컬 + 원격)
  • GitHub Release
  • 갱신된 pkgdown 사이트

완료 조건.

  • 태그와 Release 가 생성되어 있다 (성공 기준 G7)
  • pkgdown 사이트가 v0.2.0 을 반영한다
  • 공개 tarball 에서 README hash check 가 문서화된 값을 낸다

16.6 Step 11.5 — 종료 로그 및 v0.3 인계

항목 값
모드 단일
소요 ~20 분
의존 11.4

목표. 작업 전체를 닫고, 다음 사람(또는 6 개월 후의 자신)이 이어받을 수 있게 만든다.

작업.

  1. 성공 기준 G1–G7 최종 검증표 작성 — 각 기준 × 증거 × 판정. Ch.16 의 체크리스트를 채운다
  2. v0.3 백로그 정리
    • 원장의 deferred-v0.3 행 전부가 GitHub Issue 로 등록되어 있는가
    • blueprint ch.24 의 v1.x 항목 중 우선순위
    • 리뷰 Minor 발견
    • Phase 실행 중 발견한 개선 아이디어
    • 각 Issue 에 라벨과 근거 링크
  3. 인계 문서 — log/log-version-up-2026-08-14/CLOSEOUT.md
    • 이번 작업이 무엇을 바꿨나 (한 페이지)
    • 로그 지도 — 어느 로그에 무엇이 있는지
    • 알려진 한계 — v0.2.0 이 해결하지 않은 것
    • v0.3 시작점 — 무엇부터 하면 되는지
    • 재발 방지 장치 — CI 알림, branch protection, fixture 생성 파이프라인이 어디 있고 어떻게 쓰는지
  4. 회고 — 계획 대비 실제. 어느 Phase 가 예상보다 길었나? 어느 Step 이 분할됐나? 다음 계획을 세울 때 반영할 것
  5. 로그 폴더 정리 — evidence/, artifacts/, decisions/, review-packet/ 이 정돈되어 있는지. 임시 파일 제거

산출물.

  • log/log-version-up-2026-08-14/CLOSEOUT.md
  • G1–G7 최종 검증표
  • GitHub Issues (v0.3 백로그)
  • 회고

완료 조건.

  • G1–G7 전부에 증거와 판정이 있다
  • v0.3 백로그가 Issue 로 등록되어 있다
  • CLOSEOUT 이 자기 완결적이다 (이 계획서를 안 읽어도 상황 파악 가능)
  • 로그 폴더가 정돈되어 있다
