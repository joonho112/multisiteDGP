10  Phase 5 — 테스트 스위트 재구축

10.1 목표

기본 테스트 실행이 실제로 통계적 정확성을 검증하게 만든다. 성공 기준 G3 — 기본 devtools::test() 의 skip ≤ 3, 각각 문서화된 사유 를 달성한다.

현재 문제는 코드가 아니라 게이트다 (Ch.1 C-2). 게이트를 켜면 로컬에서 전부 통과한다. 따라서 이 Phase 의 본질은 테스트를 새로 쓰는 것이 아니라 이미 있는 테스트가 실행되게 만드는 것 이며, 그 과정에서 비용을 감당 가능한 수준으로 낮추는 것이다.

Step 수 8 (5.1 – 5.8)
누적 시간 ~150 분
선행 Phase Phase 3 (D3 결정)
종료 로그 006_phase05-test-suite-rebuild.qmd
병렬 가능 Phase 4, Phase 7 과 병렬 진행 가능
NotePhase 4 와의 조율

Step 5.5 (snapshot 안정화) 는 Phase 4 Step 4.5 와 겹친다. Phase 4 가 snapshot 아티팩트를, Phase 5 가 snapshot 테스트 코드를 담당한다. 두 Phase 를 병렬로 돌린다면 Step 5.5 는 Step 4.5 이후로 배치한다.

10.2 Step 5.1 — skip 게이트 1 차 제거: 비용이 낮은 것

항목 값
모드 단일
소요 ~20 분
의존 D3 결정, Step 2.2

목표. D3 이 “그대로 켠다” 로 분류한 테스트에서 게이트를 제거한다. 실행 비용이 실제로 낮은데 관성으로 게이트되어 있던 것들이다.

작업.

  1. D3 분류 ①(“그대로 켠다”) 에 해당하는 테스트에서 skip_if_not_slow() / skip_if_not_property() 호출 제거
  2. 제거 후 기본 스위트 실행 — 시간 증가분 측정
  3. 시간 예산(D3 이 정한 값, 권고 3 분) 대비 여유 확인
  4. 게이트 제거로 드러나는 실패가 있으면 원장에 등재하고 Phase 7 로 넘긴다. 여기서 고치지 않는다 — 이 Step 은 게이트 작업이다

산출물.

  • 게이트가 제거된 테스트 파일들
  • evidence/phase05/gate-removal-batch1.md — 제거 목록 + 시간 영향 + 새로 드러난 실패

완료 조건.

  • D3 분류 ① 전체에서 게이트가 제거되어 있다
  • 기본 스위트 실행 시간이 측정되어 있다
  • 새로 드러난 실패가 원장에 등재되어 있다

10.3 Step 5.2 — slow 테스트 비용 절감 ①: 표준화 계약 (T13–T17)

항목 값
모드 단일
소요 ~20 분
의존 5.1

목표. 표준화 계약 테스트 T13(ALD) · T14(Mixture) · T15(Student-t) · T16(SkewN) · T17(PMSlab) 를 검정력을 유지하면서 기본 스위트에 넣을 수 있게 만든다.

이 다섯 개가 package 의 핵심 과학적 주장 — “여덟 shape 가 단위분산 규약을 공유한다” — 을 검증한다. 기본 실행에서 빠져 있으면 안 된다.

작업.

  1. 각 테스트의 현재 비용 구조 분석 — 표본 크기, 반복 수, 파라미터 격자 크기 중 무엇이 지배적인가
  2. 검정력 보존 축소 — 표본 크기를 줄이면 tolerance 를 그에 맞게 넓혀야 한다. 축소 후에도 실제 위반을 잡을 수 있는지 확인: 의도적으로 표준화를 깨뜨린 값을 넣어 테스트가 실패하는지 검증 (mutation 검사)
  3. 축소한 버전을 기본 스위트에, 전수 격자 버전을 확장 스위트에 남긴다 (D3 분류 ③ “분할”)
  4. 각 테스트에 tolerance 선택 근거를 주석으로 남긴다 — helper-tolerances.R 를 활용
  5. 5 개 각각 재실행해 통과 확인

산출물.

  • 수정된 테스트 5 개 (기본 + 확장 분할)
  • evidence/phase05/standardization-test-power.md — 축소 전후 검정력 비교 + mutation 검사 결과

완료 조건.

  • T13–T17 이 기본 스위트에서 실행된다
  • 각 테스트가 mutation 검사를 통과한다 (의도적 위반을 잡아낸다)
  • 축소로 인한 시간 절감이 수치화되어 있다

10.4 Step 5.3 — slow 테스트 비용 절감 ②: 분포 검정 (T1b, T4, T9, T10, T11)

항목 값
모드 단일
소요 ~20 분
의존 5.2

목표. 분포 검정 계열을 같은 방식으로 처리한다.

대상.

테스트 검증 대상 비용 원인
T1b Engine A2 Gaussian KS binomial gate 반복 수
T4 dependence none 의 Spearman 순열 envelope 순열 반복
T9 기본 true_dist 가 Gaussian (Shapiro binomial gate) 반복 수
T10 nj_min truncation + multi-rep 평균 반복 수 (로그에서 매우 긴 실행 확인)
T11 JEBS Paradigm A 전체 격자의 I envelope 격자 크기

작업.

  1. binomial gate 방식 테스트(T1b, T9)는 gate 파라미터 재설계 — 반복 수와 허용 실패율의 조합. 반복을 줄이면서 1 종 오류율을 유지하는 조합 탐색
  2. T10 은 로그상 가장 긴 테스트 중 하나. 반복 수를 줄이고 전수는 확장 스위트로
  3. T11 은 격자를 대표점으로 축소하고 전수 격자는 확장 스위트로
  4. T4 는 순열 반복 수 조정
  5. 각각 mutation 검사

산출물.

  • 수정된 테스트 5 개
  • evidence/phase05/distributional-test-tuning.md — gate 파라미터 재설계 근거

완료 조건.

  • 5 개 전부 기본 스위트에서 실행된다
  • binomial gate 의 1 종 오류율이 계산되어 기록되어 있다
  • mutation 검사 통과

10.5 Step 5.4 — property 테스트 정리

항목 값
모드 단일
소요 ~20 분
의존 5.1, Step 1.3 (hedgehog 설치)

목표. P01–P12 core invariant 를 기본 스위트에 넣고, hedgehog 의존을 정리한다.

작업.

  1. Step 2.2 의 확인 결과(hedgehog 부재 시 어떤 경로로 통과했는지)를 반영. 만약 hedgehog 없이는 실질 검증이 없었다면 그동안의 통과는 가짜였으므로 원장에 등재
  2. hedgehog 를 Suggests 로 유지할지 결정 (D3 이 정했으면 그대로)
    • 유지 → 미설치 시 명확한 skip + CI 에는 반드시 설치
    • 제거 → 자체 생성기로 대체. P01–P12 각각에 결정론적 대표 케이스 + 소수의 무작위 케이스
  3. P01–P12 를 기본 스위트로 이동. 케이스 수를 조정해 시간 예산 안에 들어가게
  4. P10 (A2 fixture 비트 동일성) 은 Phase 4 의 해시 계약 변경 영향을 받는다. Phase 4 결과와 정합 확인
  5. 각 property 에 대해 mutation 검사

산출물.

  • 수정된 test-property-core-invariants.R
  • evidence/phase05/property-test-audit.md — hedgehog 처리 결정 + 케이스 수 + mutation 결과

완료 조건.

  • P01–P12 가 기본 스위트에서 실행된다
  • hedgehog 처리 방침이 구현되고 문서화되어 있다
  • P10 이 Phase 4 의 해시 계약과 정합한다

10.6 Step 5.5 — snapshot 테스트 안정화

항목 값
모드 단일
소요 ~20 분
의존 Step 4.5 (Phase 4 병렬 시)

목표. snapshot 테스트가 플랫폼과 무관하게 안정적으로 통과하게 만든다. Phase 4 가 아티팩트를 고쳤다면 이 Step 은 테스트 코드 를 고친다.

작업.

  1. helper-snapshots.R 의 래퍼 검토 — 마스킹 규칙(<VERSION>, <R>)이 충분한가?
  2. 변동 요소 전수 조사 — snapshot 에 들어가는 모든 값 중 환경 의존적인 것: 경로, 시간, locale, 부동소수점 표시, 해시
  3. 각 변동 요소에 대해: 마스킹 / 제거 / 유지(사유 기록) 중 하나 배정
  4. scenario_audit() 의 PASS/WARN/FAIL 카운트가 snapshot 에 들어가는 것이 적절한지 재검토 — 이것은 유용한 회귀 검증이지만 임계값 근처 값에서 불안정하다. Step 2.7 의 API 감사 결과 반영
  5. test-snapshot-errors.R — 오류 메시지 snapshot. 메시지 변경에 민감한 것이 의도인지 확인
  6. 세 플랫폼 검증 (Windows 는 Phase 6)

산출물.

  • 수정된 snapshot 테스트 + helper
  • evidence/phase05/snapshot-variance-sources.csv — 변동 요소 × 처리

완료 조건.

  • snapshot 의 모든 변동 요소가 분류·처리되어 있다
  • Linux · macOS 에서 snapshot 테스트가 통과한다
  • 남은 환경 의존 값에 사유가 있다

10.9 Step 5.8 — 회귀 테스트 추가 및 게이트 최종 정리

항목 값
모드 단일
소요 ~20 분
의존 5.1 – 5.7

목표. 원장의 각 결함에 회귀 테스트를 붙이고, 남은 skip 을 최종 정리한다.

작업.

  1. 회귀 테스트 — 원장의 P0/P1 각 행에 대해, 그 결함이 재발하면 잡히는 테스트가 있는가? 없으면 추가. Phase 7 이 고칠 결함에 대해서는 먼저 실패하는 테스트를 쓴다 (Phase 7 이 통과시킨다)
  2. 남은 skip 최종 정리 — 기본 스위트를 돌려 skip 목록 확인. 목표는 ≤ 3
    • 남는 것 각각에 사유를 테스트 파일 주석과 evidence/ 문서 양쪽에 기록
    • skip_if_not_validation(), skip_if_api_missing() 이 여전히 필요한지 검토. 안 쓰이면 helper 에서 제거
  3. 기본 스위트 최종 시간 측정 — D3 의 시간 예산 준수 확인
  4. 확장 스위트 정의 확정 — extended-tests workflow 가 무엇을 돌리는지 명확히. Phase 6 이 이 정의를 쓴다
  5. 전체 스위트 2 회 연속 실행해 플레이키 테스트 탐지

산출물.

  • 회귀 테스트 파일들
  • 정리된 helper-skip-policy.R
  • evidence/phase05/final-skip-inventory.md — 남은 skip × 사유
  • evidence/phase05/suite-timing-final.md — 기본/확장 스위트 시간

완료 조건.

  • 기본 스위트 skip ≤ 3, 각각 사유 기록 (성공 기준 G3)
  • 원장의 P0/P1 각 행에 회귀 테스트가 대응한다
  • 기본 스위트가 시간 예산 안에 든다
  • 2 회 연속 실행에서 결과가 동일하다 (플레이키 없음)
